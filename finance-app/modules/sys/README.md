# Поток E — Сервис и инфраструктура (`modules/sys`, `tools/`, `tests/`, `*.bat`)

## Задачи
1. **Постоянный сервер.** `docker-compose.yml` для Synology (MostServer: порты 5000/5001 — DSM) на `node:22-alpine`, том с папкой программы, автоперезапуск; инструкция для сисадмина в `docs/DEPLOY.md`. Вариант без Docker — облачный VPS (инструкция).
2. **Доступ из интернета.** Проверить `start-internet.bat` / `tools/serve-internet.js` с `pushd` (запуск из `\\MostServer\...`), постоянный адрес через именованный туннель Cloudflare — инструкция. Режим `DEV_USER` должен оставаться выключенным за туннелем (ядро уже это проверяет — покрыть тестом).
3. **Бэкапы.** Ежедневная копия в Google Drive (`tools/backup-gdrive.ps1`) — задача планировщика по кнопке «Настроить» (bat), проверка восстановления из копии на тестовой базе.
4. **Уведомления.** Функция `notify(ctx, { userIds, text, link })` в `modules/sys/server.js`: очередь `sysOutbox`, отправка ботом Telegram (токен и chat_id пользователей в настройках модуля — только владелец), повторы при ошибке. Экран «Состояние системы» для владельца: версия, база, размер, последний бэкап, адрес туннеля, очередь уведомлений.
5. **Тесты.** Обновить `tests/api_test.sh` под модули (сейчас 128 проверок): вход через `DEV_USER`, права ролей на `/api/pm`, закрытость коллекций модулей через общий API.

Секреты (токен бота) — не в git; хранятся в `data/` и в настройках.

**Обновление 24.09.2026 (решения директора, `docs/ARCHITECTURE.md`):** сервер — только MostServer/Docker (без
VPS-варианта), уведомления отложены, ядро перешло на SQLite (`erp/main`, слито в эту ветку). Ниже — что из
пункта 1–5 в итоге сделано.

## Сделано

1. **`docker-compose.yml`** (корень) — `node:24-alpine` (SQLite в 22-й версии ещё под экспериментальным флагом,
   в 24-й без него) без сборки образа, код монтируется томом (**на локальный диск NAS, не через SMB** — WAL
   нужны файловые блокировки), `restart: unless-stopped`, healthcheck по `/api/status`, порт 3000 (не 5000/5001
   — они DSM). Опциональный сервис `cloudflared` — постоянный туннель прямо в Docker.
   `docs/DEPLOY.md` переписан как пошаговый runbook сисадмину: установка, обновление версии, откат, куда
   смотреть логи, восстановление из бэкапа — без облачного варианта (по решению директора, одна ссылка на
   казахстанских провайдеров оставлена на случай, если понадобится).
2. **Доступ из интернета** — проверено: `start-internet.bat` (`pushd "%~dp0"`) и `tools/serve-internet.js`
   (все пути от `__dirname`) не зависят от текущей директории запуска. Безопасность dev-режима за туннелем —
   тест ниже.
3. **Бэкапы** — переведены на SQLite вместе с ядром:
   - `install-backup-task.bat` (корень) — регистрирует ежедневную задачу Планировщика Windows (03:00) на
     `tools\backup-gdrive.ps1`.
   - `tools/backup-gdrive.ps1` переписан под `data/db.sqlite`: согласованный снимок через `VACUUM INTO`
     (сервер можно не останавливать), из копии одним запросом удаляется таблица сессий, дальше как раньше —
     zip с прикреплёнными файлами, хранится `-Keep` последних копий.
   - `tests/backup_gdrive_test.ps1` (переписан под SQLite) собирает тестовую базу той же схемой, что
     `lib/store.js` (`docs`/`kv`), гоняет через реальный `tools/backup-gdrive.ps1` на тестовых путях (реальный
     `\\MostServer` и Google Drive не трогает), проверяет: снимок создан, `sessions` вычищены, `settings` и
     документы (`users`, `ops`) на месте, файлы скопированы, лишние копии сверх `-Keep` удаляются.
4. **Уведомления — отложены** (решение директора, п. 2 «Решений директора» в `docs/ARCHITECTURE.md`: «пока не
   делаем — ни Telegram, ни WhatsApp»). Реализованный было модуль (`notify`, очередь `sysOutbox`, Telegram Bot
   API, экран очереди) убран из `modules/sys/server.js` и `ui.js` целиком — не оставлял отключённым файлом,
   чтобы не путать: код без ссылок в git-истории этой ветки, при необходимости поднять — коммит до этого
   удаления. `modules/sys/CORE-REQUESTS.md` — заявка ведущей сессии убрать устаревшую строку `sys.notify` из
   таблицы событий в `docs/ARCHITECTURE.md`.
   Что осталось от задачи — экран **«Состояние системы»** (`modules/sys/ui.js`, только владелец): версия, путь
   и размер `data/db.sqlite`, число и время последнего бэкапа, адрес туннеля (если запущен), явный флаг, если
   `DEV_USER` включён на этом сервере. `GET /api/sys/status` — только владелец.
5. **Тесты** — `tests/api_test.sh` (было 128 проверок), новые/актуальные разделы:
   - «модуль pm: роли» — `PM_ROLES`/`canCreate`/`isManager` из `modules/pm/domain.js` на живом `/api/pm/*`:
     owner/partner/accountant/secretary/pm/gip видят сводку, `staff` — нет; создавать проект может только
     leader/pm/gip; редактировать карточку — только ГИП/ПМ этого проекта или руководитель.
   - «закрытые коллекции модулей» — `GET /api/pmProjects`, `pmItems`, `pmBlockers`, `hrTimesheets`, `crmLeads`,
     `kbNews` через общий `/api/<коллекция>` — везде 404, даже для владельца.
   - «модуль sys» — только `/api/sys/status`, доступ владельцу, проверка, что база теперь `db.sqlite`.
   - «DEV_USER» — отдельный перезапуск сервера: вход без пароля работает только с `127.0.0.1` и без
     `TRUST_PROXY`; заголовки `CF-Connecting-IP`/`X-Forwarded-For` (как за туннелем) блокируют dev-вход;
     `TRUST_PROXY=1` (именно так его выставляет `serve-internet.js` за туннелем) отключает dev-вход полностью,
     даже с локального адреса — гарантия для реального продакшена.

## Как проверить

```
set DATA_DIR=data-dev\sys& set DEV_USER=owner& set PORT=3105& node server.js
```
Открыть `http://localhost:3105`, в интерфейсе — раздел «Сервис → Состояние системы» (виден только владельцу,
`devrole=owner`). База при первом запуске создастся сразу как `data-dev\sys\db.sqlite`.

```
bash tests/api_test.sh                                          # требует python3 на PATH
powershell -NoProfile -ExecutionPolicy Bypass -File tests\backup_gdrive_test.ps1
```
`node --check modules/sys/server.js modules/sys/ui.js` — без ошибок. Оба файла и слияние с `erp/main`
проверены вручную: сервер стартует на SQLite, `/api/sys/status` отдаёт `dbFile` с `.sqlite`, права по ролям —
через `curl` на dev-сервере и полный прогон `api_test.sh`.

`docker-compose.yml` и `docs/DEPLOY.md` — Docker здесь не установлен, синтаксис проверен вручную; перед первым
реальным разворачиванием на Synology стоит один раз прогнать `docker compose config` и `docker compose up` на
месте.

## Что осталось

- Прогнать `docker-compose.yml` на реальном Synology (Container Manager) — здесь Docker недоступен, проверено
  только вручную по инструкции.
- Реальный туннель Cloudflare — не поднимался (поток E: только скрипты и инструкции, не запускать самому).
- `modules/sys/CORE-REQUESTS.md` ждёт правки ведущей сессии (устаревшая строка `sys.notify` в
  `docs/ARCHITECTURE.md`).
- Уведомления — отложены директором, не в этой поставке; если решение изменится, начинать заново (было готовое
  решение на Telegram Bot API + `sysOutbox`, в истории git этой ветки до его удаления).
- `seed/` в этом чекауте пуст (реальные данные компании не коммитятся) — часть уже существующих проверок
  `api_test.sh` (не из этого потока), завязанных на количество засеянных счетов/контрагентов/фиксированный id
  `ct-001`, падает без него, независимо от изменений этого потока.
