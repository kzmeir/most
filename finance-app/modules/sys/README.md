# Поток E — Сервис и инфраструктура (`modules/sys`, `tools/`, `tests/`, `*.bat`)

## Задачи
1. **Постоянный сервер.** `docker-compose.yml` для Synology (MostServer: порты 5000/5001 — DSM) на `node:22-alpine`, том с папкой программы, автоперезапуск; инструкция для сисадмина в `docs/DEPLOY.md`. Вариант без Docker — облачный VPS (инструкция).
2. **Доступ из интернета.** Проверить `start-internet.bat` / `tools/serve-internet.js` с `pushd` (запуск из `\\MostServer\...`), постоянный адрес через именованный туннель Cloudflare — инструкция. Режим `DEV_USER` должен оставаться выключенным за туннелем (ядро уже это проверяет — покрыть тестом).
3. **Бэкапы.** Ежедневная копия в Google Drive (`tools/backup-gdrive.ps1`) — задача планировщика по кнопке «Настроить» (bat), проверка восстановления из копии на тестовой базе.
4. **Уведомления.** Функция `notify(ctx, { userIds, text, link })` в `modules/sys/server.js`: очередь `sysOutbox`, отправка ботом Telegram (токен и chat_id пользователей в настройках модуля — только владелец), повторы при ошибке. Экран «Состояние системы» для владельца: версия, база, размер, последний бэкап, адрес туннеля, очередь уведомлений.
5. **Тесты.** Обновить `tests/api_test.sh` под модули (сейчас 128 проверок): вход через `DEV_USER`, права ролей на `/api/pm`, закрытость коллекций модулей через общий API.

Секреты (токен бота) — не в git; хранятся в `data/` и в настройках.

## Сделано

1. **`docker-compose.yml`** (корень) — `node:22-alpine` без сборки образа, код монтируется томом, `restart: unless-stopped`,
   healthcheck по `/api/status`, порт по умолчанию 3000 (не 5000/5001 — они DSM). Закомментированный сервис
   `cloudflared` — постоянный туннель прямо в Docker, включается по инструкции. `docs/DEPLOY.md` — разворачивание
   на Synology и как альтернатива для сервера без Docker: облачный VPS (Node.js + systemd, без открытого порта в
   интернет).
2. **Доступ из интернета** — проверено: `start-internet.bat` (`pushd "%~dp0"`) и `tools/serve-internet.js`
   (все пути от `__dirname`) не зависят от текущей директории запуска, включая запуск по сетевому пути
   `\\MostServer\...`. Правку кода это не потребовало. Безопасность dev-режима за туннелем — тест ниже.
3. **Бэкапы**:
   - `install-backup-task.bat` (корень) — регистрирует ежедневную задачу Планировщика Windows (03:00) на
     `tools\backup-gdrive.ps1`, по образцу `install-autostart.bat`.
   - Найдены и исправлены 2 бага в `tools/backup-gdrive.ps1`: (а) `db.json` с BOM (Notepad/PowerShell) ломал
     `JSON.parse` в Node — добавлено снятие BOM; (б) штамп времени без секунд склеивал два бэкапа подряд в один
     файл — добавлены секунды. Оба найдены тестом восстановления, `tests/backup_gdrive_test.ps1`, на тестовых
     путях (реальный `\\MostServer` и Google Drive не трогает): собирает zip, разворачивает, проверяет, что
     `db.json` без `sessions`, пользователи и операции на месте, файлы скопированы, и что лишние копии сверх
     `-Keep` удаляются.
4. **Уведомления Telegram** — `modules/sys/server.js`:
   - `ctx.modules.sys.notify(ctx, { userIds, text, link })` — кладёт в `sysOutbox` и сразу пробует отправить.
   - `deliver()` шлёт через `https.request` на `api.telegram.org` (без внешних зависимостей); при ошибке помечает
     `pending` (до 5 попыток) или `failed`; фоновый таймер повторяет зависшие `pending` каждые 5 минут.
   - Токен бота и chat_id сотрудников — `settings.sys` (в `data/db.json`, не в git), только владелец:
     `GET/PUT /api/sys/settings` (токен отдаётся наружу только последними 4 символами).
   - `GET /api/sys/status` (владелец): версия, путь и размер базы, число и время последнего бэкапа, адрес
     туннеля (если запущен), явный флаг, если `DEV_USER` включён на этом сервере, счётчики очереди.
   - `GET /api/sys/outbox`, `POST /api/sys/outbox/:id/retry`, `POST /api/sys/notify/test` (шлёт тест себе).
   - Экран **«Состояние системы»** (`modules/sys/ui.js`) — виден только владельцу: карточка статуса, таблица
     очереди с повтором по кнопке, форма токена бота, таблица «пользователь → chat ID».
5. **Тесты** — `tests/api_test.sh` (было 128 проверок, стало 173), новые разделы:
   - «модуль pm: роли» — `PM_ROLES`/`canCreate`/`isManager` из `modules/pm/domain.js` на живом `/api/pm/*`:
     owner/partner/accountant/secretary/pm/gip видят сводку, `staff` — нет; создавать проект может только
     leader/pm/gip; редактировать карточку — только ГИП/ПМ этого проекта или руководитель.
   - «закрытые коллекции модулей» — `GET /api/pmProjects`, `pmItems`, `pmBlockers`, `sysOutbox`, `hrTimesheets`,
     `crmLeads`, `kbNews` через общий `/api/<коллекция>` — везде 404, даже для владельца.
   - «модуль sys» — права на `/api/sys/status`/`settings` (только владелец), тестовое уведомление реально
     кладётся в очередь.
   - «DEV_USER» — отдельный перезапуск сервера: вход без пароля работает только с `127.0.0.1` и без
     `TRUST_PROXY`; заголовки `CF-Connecting-IP` / `X-Forwarded-For` (как за туннелем) блокируют dev-вход;
     `TRUST_PROXY=1` (именно так его выставляет `serve-internet.js` за туннелем) отключает dev-вход полностью,
     даже с локального адреса — это и есть гарантия для реального продакшена.

## Как проверить

```
set DATA_DIR=data-dev\sys& set DEV_USER=owner& set PORT=3105& node server.js
```
Открыть `http://localhost:3105`, в интерфейсе — раздел «Сервис → Состояние системы» (виден только владельцу,
`devrole=owner`). Кнопка «Тест уведомления себе» — без настроенного токена уйдёт в очередь со статусом
«пропущено» и причиной; впишите токен реального бота и свой chat_id, чтобы увидеть «отправлено».

```
bash tests/api_test.sh                                          # требует python3 на PATH
powershell -NoProfile -ExecutionPolicy Bypass -File tests\backup_gdrive_test.ps1
```
`node --check modules/sys/server.js modules/sys/ui.js` — без ошибок. Оба файла проверены вручную через
`curl` на dev-сервере (статус, настройки, тестовое уведомление, повтор, закрытость коллекций, роли) — см. раздел
«Сделано».

`docker-compose.yml` и `docs/DEPLOY.md` — Docker здесь не установлен, синтаксис проверен вручную (нет
`docker compose config` под рукой); перед первым реальным разворачиванием на Synology стоит один раз прогнать
`docker compose config` и `docker compose up` на месте.

## Что осталось

- Прогнать `docker-compose.yml` на реальном Synology (Container Manager) — здесь Docker недоступен, проверено
  только вручную по инструкции.
- Реальный Telegram-бот и постоянный туннель Cloudflare — не поднимались (по условиям потока E: только скрипты
  и инструкции, не запускать самому).
- Удаление одной пары `userId → chat_id` в «Chat ID сотрудников» — сейчас `PUT /api/sys/settings` только
  добавляет/обновляет пары, пустое значение не удаляет существующую; для расчистки пока проще стереть всю
  таблицу `settings.sys.chats` через API.
- `seed/` в этом чекауте пуст (реальные данные компании не коммитятся) — часть уже существующих проверок
  `api_test.sh` (не из этого потока), завязанных на количество засеянных счетов/контрагентов/фиксированный id
  `ct-001`, падает без него. Новые разделы этого потока от `seed/` не зависят и проходят полностью.
