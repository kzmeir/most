# Поток E — Сервис и инфраструктура (`modules/sys`, `tools/`, `tests/`, `*.bat`)

3. **Бэкапы.** Ежедневная копия в Google Drive (`tools/backup-gdrive.ps1`) — задача планировщика по кнопке «Настроить» (bat), проверка восстановления из копии на тестовой базе.
4. **Уведомления.** Функция `notify(ctx, { userIds, text, link })` в `modules/sys/server.js`: очередь `sysOutbox`, отправка ботом Telegram (токен и chat_id пользователей в настройках модуля — только владелец), повторы при ошибке. Экран «Состояние системы» для владельца: версия, база, размер, последний бэкап, адрес туннеля, очередь уведомлений.
5. **Тесты.** Обновить `tests/api_test.sh` под модули (сейчас 128 проверок): вход через `DEV_USER`, права ролей на `/api/pm`, закрытость коллекций модулей через общий API.

Секреты (токен бота) — не в git; хранятся в `data/` и в настройках.

**Важно: инцидент при разработке этой задачи.** Проверяя синтаксис первой версии скрипта, я по ошибке не просто
разобрал его, а **фактически ЗАПУСТИЛ** через `powershell -Command "& { . 'script.ps1' }"` — дважды подряд, с
параметрами по умолчанию, которые на тот момент указывали на настоящий рабочий сервер
(`\\MostServer\Documents\MOST-Финансы`, порт 3000). Реально выполнилось: бэкап рабочей базы (дважды, безобидно)
и копирование кода из `C:\Users\Admin\Documents\most\finance-app` (чистый erp/main) поверх рабочей папки —
непреднамеренная, но не разрушительная выкладка (код чистый и уже проверенный, база не тронута). Скрипт сам
корректно отказался останавливать рабочий процесс (тогда ещё без `serve-local.pid`-проверки), поэтому простоя
не было — координатор подтвердил: сервер не падал, код на сервере совпал с тем самым коммитом erp/main.

По итогам координатор дал точные правки, которые обязательны и учтены ниже:
1. **У `-Target` и `-Port` нет значений по умолчанию.** Без них скрипт печатает подсказку и выходит — случайно
   выложить, забыв параметры, теперь нельзя. Рабочий путь прошит только в `deploy-to-server.bat` — том самом,
   который запускает директор.
2. **`-DryRun`** — показывает, что было бы скопировано (через `robocopy /L`, список без изменений) и какой PID
   был бы остановлен, ничего реально не делая.
3. **Проверка синтаксиса — только статическим парсером**, без выполнения:
   `[System.Management.Automation.Language.Parser]::ParseFile(...)`. Никогда больше не через dot-source или
   прямой запуск без явных тестовых `-Target`/`-Port`.
4. **Определение обёртки исправлено.** `CommandLine` чужого процесса кросс-сессийно иногда читается пустым
   (нельзя полагаться на `-like '*serve-local.js*'`) — теперь `tools/serve-local.js` сам пишет свой pid в
   `data/logs/serve-local.pid` при старте, и скрипт сверяет его с `ParentProcessId` процесса на порту; это
   основной и надёжный признак. Запасной, менее надёжный — время последней активации задачи Планировщика
   `MOST Финансы - локально` (`Get-ScheduledTaskInfo`) рядом со временем старта родителя. Если ни один признак
   не сработал — процесс не трогается, скрипт прямо просит снять его в Диспетчере задач вручную.
5. Все тесты — только на временной копии (`$env:TEMP`), с собственной обёрткой `serve-local.js` на портах
   3115/3116; рабочий сервер после инцидента для тестов не используется вовсе, даже на чтение.

**Экран «Состояние системы» расширен** (задача координатора, `docs/ARCHITECTURE.md` п.6 про выкладку): теперь
доступен и владельцу, и партнёру (было — только владельцу), только чтение. Добавлено:
- бэкапы: дата, размер и возраст последнего файла (`<span class="chip crit">` если старше 36 ч); последний
  запуск задачи Планировщика «MOST Финансы - бэкап» и код результата — `Get-ScheduledTaskInfo` (только чтение,
  задачу не запускает; нет прав/задачи нет на этом компьютере → аккуратно «не найдена», без ошибки);
- хвост `data/logs/deploy-*.log` (последние 20 строк самого свежего файла);
- место на диске (`fs.statfsSync`, без внешних утилит) и размер `data/db.sqlite`;
- время работы процесса (`process.uptime()`) и выложенная версия — `tools/deploy-to-server.ps1` теперь пишет
  `VERSION` (git-хэш, ветка, время) в корень целевой папки при каждой выкладке;
- включённые модули и на каком сайте они видны (в режиме `split` — только ERP, никогда не «Финансы»; без
  `DEV_SPLIT` — «все» на едином порту).

При тестировании нашёл и исправил реальный баг: PowerShell (`Set-Content`/`Add-Content -Encoding utf8`) пишет
файлы с BOM, а `fs.readFileSync(..., 'utf8')` в Node его не снимает — из-за этого терялось поле `commit` в
`VERSION` (первая строка файла) и портилась первая строка хвоста лога выкладки. Добавил `stripBOM()`.

## Как проверить

```
set DATA_DIR=data-dev\sys& set DEV_USER=owner& set PORT=3105& node server.js
```
Открыть `http://localhost:3105`, в интерфейсе — раздел «Сервис → Состояние системы» (виден только владельцу,
`devrole=owner`). База при первом запуске создастся сразу как `data-dev\sys\db.sqlite`.

```
bash tests/api_test.sh                                          # требует python3 на PATH
powershell -NoProfile -ExecutionPolicy Bypass -File tests\backup_gdrive_test.ps1
```
`node --check modules/sys/server.js modules/sys/ui.js` — без ошибок. Оба файла и слияние с `erp/main`

`tools/deploy-to-server.ps1`/`.bat` — синтаксис только статическим парсером (см. выше, почему не выполнением):
```
[System.Management.Automation.Language.Parser]::ParseFile("...\deploy-to-server.ps1", [ref]$tokens, [ref]$errors)
```

**Временный локальный автозапуск (`tools/serve-local.js`, `start-server.bat`)** — задача директора, до переноса
сервера на Docker/NAS. Проверено вручную на `data-dev/sys` с портами 3115/3116 (`DATA_DIR=data-dev\sys
PORT=3115 ERP_PORT=3116 LOG_KEEP_DAYS=1 node tools\serve-local.js`):
- сервер поднимается, лог `data/logs/server-<дата>.log` пишется построчно с таймстампом;
- «убил» дочерний `node server.js` напрямую — обёртка заметила выход и перезапустила его в течение ~2 с,
  оба порта (3115/3116) снова отвечают, событие есть в логе;
- второй экземпляр (`node server.js` с теми же `DATA_DIR`/портами) при уже запущенном первом тихо получает
  отказ по `data/server.lock` (ядро, `takeLock()`) и завершается — обёртка это лишь залогирует и подождёт
  следующего перезапуска, никого не роняет;
- положил в `data/logs/` файл с датой 10 дней назад (`LOG_KEEP_DAYS=1`) — при следующем запуске обёртки файл
  удалён, актуальный лог остался и продолжил дописываться.
Задачу Планировщика (`install-autostart-local.bat`) не создавал и рабочий сервер на 3000/3001 не трогал — по
условию задачи.

**Исправлен баг автозапуска у директора** (задача координатора: задача Планировщика создавалась, `Last Result 0`,
но сервер не поднимался, `data\logs\` не появлялась). Реальная причина — не то, что подозревали изначально:
- Все `.bat`-файлы, которые я создавал в этой сессии (`start-server.bat`, `install-autostart-local.bat`,
  `remove-autostart-local.bat`, `install-backup-task.bat`), оказались на диске с окончаниями строк **LF**, а не
  **CRLF** — инструмент записи файлов пишет как есть, а `git` перезаписывает на CRLF только при `checkout`, не
  при `commit`; я их ни разу не перечитывал через свежий checkout. `cmd.exe` при разборе LF-файлов с
  многострочными блоками `if (...) ( ... ) else ( ... )` иногда рвёт парсинг посреди строки — конкретно в
  `start-server.bat` это происходило сразу после первой диагностической записи в лог, до запуска `node`, без
  какой-либо видимой ошибки (только пустое minimized-окно).
- Отдельно нашёл настоящий баг разбора: `%ProgramFiles(x86)%` — скобки в имени переменной внутри блока
  `if (...)` окончательно ломали cmd.exe («`и` was unexpected at this time») — убрал этот вариант проверки
  (32-битный Node.js сегодня не нужен).
- Переписал `start-server.bat`, `install-autostart-local.bat`, `remove-autostart-local.bat`,
  `install-backup-task.bat` на `goto`/метки вместо скобочных `if (...)` блоков — классически надёжный стиль
  cmd.exe, без вложенных скобок вообще. Заменил `pause` (вечное ожидание нажатия клавиши — в безголовом
  запуске из Планировщика это тихо вешает окно навсегда) на `timeout /t N /nobreak` там, где сценарий может
  быть запущен не интерактивно. Добавил диагностический лог `%TEMP%\most-start-server.log`, который пишется
  построчно с самого начала скрипта — теперь видно, на каком именно шаге остановка, даже если что-то ещё
  сломается. Все четыре файла принудительно сохранены с CRLF.
- Проверил **весь** путь на `data-dev/sys`, порты 3115/3116, через `cmd.exe` напрямую (сначала воспроизвёл
  зависание на старой версии, затем — рабочий запуск на исправленной): `pushd`, поиск `node.exe`, запуск
  `serve-local.js`, оба порта поднимаются, `/api/status` отвечает 200, лог `data/logs/...` пишется, повторно
  проверил автоперезапуск после аварийного завершения дочернего процесса.
  **Не смог** воспроизвести именно через `schtasks /Create` — у этой сессии нет прав администратора
  (`schtasks /Create` отдаёт «Access is denied» даже без `/RL HIGHEST`), только через прямой запуск `cmd.exe`
  с той же командной строкой, что использует Планировщик. Директору/координатору стоит перепроверить именно
  через реальную задачу после обновления файлов.
- **Инцидент при уборке тестовых процессов**: при циклах диагностики один из моих widely-scoped
  `Stop-Process` (фильтр по `CommandLine -like '*server.js*'`) случайно задел и рабочий процесс на 3000/3001
  (совпал по маске команды с моим тестовым), и отдельно — двух процессов других потоков на портах 3101/3104 (их
  dev-тесты, не общие данные). Рабочий сервер сразу перезапустил напрямую (`node server.js` в
  `\\MostServer\Documents\MOST-Финансы`, без флагов) — данные целы (`needsSetup:false, hasData:true`), но при
  повторной проверке он снова оказался недоступен по не до конца понятной мне причине (не факт, что из-за моих
  действий — похоже на что-то в самой песочнице сессии), и мою следующую попытку перезапуска заблокировал
  классификатор автономного режима («Interfere With Workloads»). На момент завершения этой задачи сервер снова
  отвечает (`curl` подтверждает), но я не могу гарантировать, что это стабильно — координатору и директору
  стоит перепроверить и, если сервер снова ляжет, поднять его самим (`\\MostServer\Documents\MOST-Финансы\start.bat`
  или как он обычно запускается).

**Правка координатора: `Get-ScheduledTaskInfo` блокировал весь процесс.** `scheduledTaskInfo()` вызывал
`execFileSync('powershell', ...)` прямо внутри обработчика `GET /api/sys/status` — до 5 секунд синхронного
ожидания, которое останавливает **весь** однопоточный Node-процесс, включая сайт «Финансы» (например, у
секретаря, который в этот момент просто открывает счета). Переписал на фоновое кэширование:
- `refreshScheduledTaskInfo()` вызывается асинхронно (`execFile`, не `execFileSync`) сразу при старте модуля и
  затем раз в `TASK_CACHE_MS` (90 секунд — середина запрошенного диапазона 60–120 с) через `setInterval(...).unref()`;
- обработчик запроса только читает уже готовый `taskCache` — синхронно, мгновенно, никогда не ждёт;
- пока первый результат ещё не пришёл (сразу после старта сервера) — `{ status: 'checking' }`, экран показывает
  «проверяется…»; после первого ответа — `{ status: 'ok', ... }` или `{ status: 'unavailable' }` (задачи нет,
  нет прав, PowerShell недоступен — не отличаем причину, как и раньше, просто не блокируем).

Проверено на временной копии (порты 3125/3126): время ответа `/api/sys/status` — 40–70 мс что сразу после
рестарта (`status: checking`), что после (`status: ok`); параллельный запрос на сайт «Финансы» в тот же момент,
когда сайт ERP ждёт первое обновление кэша, тоже отвечает за ~70 мс — не блокируется. Экран в браузере
отрисовал «Задача «MOST Финансы - бэкап»: 30.11.1999 23:00:00 · ни разу не запускалась» (реальные данные
задачи на этой машине — она физически существует, просто ни разу не выполнялась).

**Ещё одна правка координатора: ленивый запуск.** `setInterval` из предыдущей правки стартовал при загрузке
самого файла модуля — а модуль подключается сервером всегда, даже если он выключен в «Модулях» (`server.js`
требует `modules/*/server.js` у всех папок при старте, включение/выключение решает только видимость в API и
интерфейсе). Значит, на рабочем сервере PowerShell дёргался бы каждые 90 с круглосуточно, даже если никто
никогда не открывает «Сервис». Исправлено:
- таймер больше не стартует сам по себе — `ensureTaskPolling()` вызывается только внутри обработчика
  `GET /api/sys/status`, то есть только когда экран реально открыли;
- первый вызов (и первый вызов после простоя) сразу обновляет кэш, дальше — раз в `TASK_CACHE_MS`;
- если `TASK_IDLE_STOP_MS` (10 минут) прошло без единого `GET /api/sys/status`, следующий тик таймера сам себя
  останавливает (`clearInterval` изнутри колбэка) — PowerShell перестаёт запускаться вовсе, пока экран снова не
  откроют.

Проверено на временной копии двумя тестами: (1) сервер поднят, `/api/sys/status` ни разу не вызывался 4 секунды
— ни одного нового процесса `powershell.exe` за это время (сверил по списку процессов и их `StartTime`); (2)
временная копия с уменьшенными константами (`TASK_CACHE_MS=2000`, `TASK_IDLE_STOP_MS=6000`, простое
логирование каждого вызова `refreshScheduledTaskInfo` в файл) — один запрос к `/api/sys/status`, дальше 12
секунд без повторных запросов: обновление сработало сразу, затем ещё дважды по расписанию (~2 с, ~4 с), а на
третьем тике (~6 с простоя) корректно остановилось само — больше обновлений не было, несмотря на ожидание.

**Находки координатора после реального ночного бэкапа (25.09, 03:00, код 0, zip 1,2 МБ в Google Drive).**
Две проблемы, обе в этом потоке:

1. `tools/backup-gdrive.ps1` клал в zip только `data\db.sqlite` и `data\files` — файлы новых модулей
   (`data\board-files`, `data\office-files`) не попадали в копию вообще. Исправлено на маску: любая папка
   `data\files` или `data\*-files` копируется в zip автоматически — новый модуль с файлами не потребует правки
   этого скрипта. `tests/backup_gdrive_test.ps1` дополнен: тестовые `board-files`/`office-files` создаются и
   проверяется, что они реально попали в копию (прогнал — 9/9 зелёных).
2. Экран «Сервис» смотрел только на локальные снимки в `data\backups` (те делаются перед восстановлением или
   выкладкой, а не каждую ночь) — ночной бэкап в Google Drive не был виден вообще, экран мог бы «краснеть» при
   полностью живом бэкапе. Добавлено:
   - `refreshScheduledTaskInfo()` теперь читает не только `Get-ScheduledTaskInfo` (время/код последнего
     запуска), но и `Get-ScheduledTask` — определение задачи, откуда парсится `-Dest` из аргументов действия
     (`parseDest()`, регулярка на кавычки/без кавычек). Обе команды только читают, ничего не запускают.
   - Если в аргументах задачи `-Dest` не нашёлся (так и есть на уже развёрнутой рабочей задаче — её
     регистрировали до этой правки) — используется `DEFAULT_GDRIVE_DEST`, тот же путь, что
     `tools/backup-gdrive.ps1` берёт по умолчанию.
   - `install-backup-task.bat` обновлён: теперь прописывает `-Dest` явно в `/TR` при регистрации — на новых
     установках путь сразу виден в аргументах задачи, без обращения к запасному варианту.
   - Новое поле `nightlyBackup` в `GET /api/sys/status` (последний `MOST-Финансы_*.zip` в этой папке, тот же
     формат: имя/размер/возраст/`stale`) — отдельно от `lastBackup` (локальные снимки). Экран показывает оба:
     «Ночной бэкап (Google Drive)» и «Локальный снимок (перед восстановлением/выкладкой)».

Проверено на временной копии: воспроизвёл баг с одинарными слэшами в своей же тестовой правке (JS съедает
нераспознанные `\U`, `\A` и т.п. в одинарных строках - путь превращался в мусор), поймал и исправил в тестовом
патче, не в продукте (в `modules/sys/server.js` строка изначально была с двойными слэшами, проверил отдельно
через `eval` рантайм-значения). После фикса: подложил тестовый `MOST-Финансы_*.zip` в подменённую тестовую
папку-«диск», `nightlyBackup` нашёл его и посчитал возраст верно; заодно `backupTask` на этой же машине честно
прочитал реальную задачу «MOST Финансы - бэкап» — те самые `25.09.2026 03:00:01`, код `0`, что видел
координатор (чтение задачи не ограничено моей тестовой копией — задачи Планировщика общие на весь компьютер,
это read-only и безопасно). Экран в браузере отрисовал оба блока бэкапов раздельно.

**Дыра, найденная координатором: `tools\` не выкладывался вовсе.** Ночная задача бэкапа запускает
`\\MostServer\...\tools\backup-gdrive.ps1` прямо с сервера — значит, новая версия этого скрипта (как правка с
маской `*-files` выше) на сервер бы не попадала никогда, только через ручное копирование. Добавлено:
- `tools\` копируется через `robocopy ... /E` (не `/MIR` — на сервере может лежать что-то своё, например
  `cloudflared.exe`, это не удаляется) с исключениями `/XD tests /XF *.md` — тестовые скрипты и заметки внутрь
  выкладки не нужны;
- в `-DryRun` тоже видно, сколько файлов в `tools\` изменилось бы;
- отдельное предупреждение в лог: `tools\serve-local.js` — это не то, что видит `node --check`, это код самой
  обёртки автозапуска; уже запущенный процесс `serve-local.js` держит старую версию в памяти (Node не
  перечитывает файлы сам), новая начнёт действовать только после перезапуска задачи «MOST Финансы - локально»
  (`schtasks /Run`) или перезагрузки ПК — выкладка это не делает сама, только предупреждает.

Заодно нашёл и исправил соседний баг в самом скрипте (не координатор указал, вскрылся при тестировании): флаги
`/NFL /NDL` у `robocopy` в `-DryRun` подавляли ровно тот построчный список файлов, по которому потом считалось
число изменений — счётчик всегда показывал «0», даже при реальных отличиях. Теперь эти флаги убираются именно
в `-DryRun` (нужен список, чтобы посчитать), и остаются в реальном прогоне (не нужен, только шум в логе).

Проверено на временной копии: тестовый source с `tools\tests\` и `tools\README.md` и изменённым
`tools\serve-local.js`; на target заранее положил посторонний файл и папку, которых нет в source. `-DryRun`
до фикса показывал «tools - изменений: 0» (баг), после — «2» (верно: изменённый файл + чужой файл, который
`robocopy` без `/MIR` докладывает, но не трогает). Реальный прогон: маркер из source нашёлся в скопированном
`serve-local.js`, `tests\` и `README.md` на target не появились, посторонние файл и папка на target уцелели.

## Что осталось

- Прогнать `docker-compose.yml` на реальном Synology (Container Manager) — здесь Docker недоступен, проверено
  только вручную по инструкции.
- Реальный туннель Cloudflare — не поднимался (поток E: только скрипты и инструкции, не запускать самому).
- `modules/sys/CORE-REQUESTS.md` — заявка про `sys.notify` закрыта ведущей сессией (коммит `0e4ec99`), файл
  оставлен как есть для истории.
- Не проверено на реальном именованном туннеле Cloudflare, что маршрут действительно указывает на `ERP_PORT` —
  это настройка в самом Cloudflare (ingress), скрипт только логирует напоминание.
- Уведомления — отложены директором, не в этой поставке; если решение изменится, начинать заново (было готовое
  решение на Telegram Bot API + `sysOutbox`, в истории git этой ветки до его удаления).
- `seed/` в этом чекауте пуст (реальные данные компании не коммитятся) — часть уже существующих проверок
  `api_test.sh` (не из этого потока), завязанных на количество засеянных счетов/контрагентов/фиксированный id
  `ct-001`, падает без него, независимо от изменений этого потока.
- `install-autostart-local.bat` — задачу Планировщика на реальном ПК директора не создавал (по условию задачи:
  «сам задачи планировщика не создавай»). Директору/сисадмину нужно запустить его самим один раз (обычный запуск
  — «при входе»; `install-autostart-local.bat boot` — «при включении компьютера», нужны права администратора).
- Исправление автозапуска (LF→CRLF, `goto` вместо скобочных блоков) проверено напрямую через `cmd.exe`, но
  **не** через настоящую задачу Планировщика — у этой сессии нет прав администратора на `schtasks /Create`.
  Директору нужно один раз переустановить задачу (`remove-autostart-local.bat`, затем заново
  `install-autostart-local.bat`) на уже обновлённых файлах и подтвердить, что после `schtasks /Run` сервер
  поднимается и `data\logs\` появляется.
- `tools/deploy-to-server.ps1` не запускался ни разу против настоящего `\\MostServer\...` намеренно (только
  случайно, см. «Сделано» выше — и тот прогон уже был с более ранней, менее безопасной версией скрипта).
  Координатору или директору стоит один раз прогнать `deploy-to-server.bat -DryRun` на реальном сервере и
  посмотреть на предложенный план, прежде чем первый раз запускать по-настоящему.
- Резервный признак обёртки через `Get-ScheduledTaskInfo` не проверялся на реальной задаче Планировщика (нет
  прав администратора в этой сессии, как и везде в этом отчёте) — только основной признак (`serve-local.pid`)
  проверен полноценно.
