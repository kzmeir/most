# Поток C — Коммерция (`modules/crm`)

Стартует после первых экранов `modules/pm`. КП (генератор) и договоры пока живут в ядре (`db.proposals`, `db.contracts`) — их читаем, новые сущности — в коллекциях модуля.

Ставки и форматы КП: память директора — ЭП 900 ₸/м² без НДС (BI бизнес), РП ЖК 5 300 ₸/м² без НДС, виллы 25–30 тыс. ₸/м² с НДС, оплата 30/30/30/10; шаблон КП — docx-генератор на `Y:` (см. историю КП в `C:\Users\Admin\Documents\Коммерческие`).

## Коллекции
`crmLeads` (источник, заказчик, объект, площадь, стадия ЭП/РП/АН, ответственный, статус: новый → расчёт → КП отправлено → торг → договор / отказ с причиной, связь с `proposals.id` и `contracts.id`), `crmPayments` (график по договору: этап, доля %, сумма, срок, привязка к этапу pm `pmProjectId + stage`, статус: ожидается / выставлен акт / оплачен), `crmTemplates` (шаблоны документов: договор, ДС, АВР, счёт — текст с полями `{{заказчик}}`, `{{сумма}}`…). `crmInbox`, `crmInboxMessages` — обращения из WhatsApp (см. раздел ниже).

## Задачи
1. Воронка лидов: канбан по статусам и таблица, конверсия КП → договор, причины отказов, средняя ставка ₸/м² по типам объектов.
2. График платежей по договору (шаблон 30/30/30/10), привязка этапов оплаты к этапам проекта; при отметке этапа в pm (`pm.item.done`) — подсказка «пора выставлять акт» (запрос бухгалтеру в `db.docs` — через CORE-REQUESTS, если нужен новый API ядра).
3. Шаблоны документов: заполнение по данным договора и проекта, выгрузка HTML для печати/PDF (как генератор КП в ядре).
4. «Договор подписан» → `ctx.modules.pm.createProject(ctx, { track, name, client, projectId, start, due }, userId)` и событие `crm.contract.signed`.
5. Отдать финансам ожидаемые поступления: функция `expectedPayments(ctx, from, to)` для прогноза денег (подключит ядро).

Права: руководители — всё; секретарь — лиды и документы; ПМ — лиды своих объектов (чтение); остальные — нет.

Ожидаемая дата: вручную → акт + срок → подписание + срок (аванс) → окончание этапа pm (план/факт) + `settings.paymentTermDays`. «Пора выставлять акт» — все пункты этапа сделаны (считается на лету; обработчик `pm.item.done` ставит `readyAt`). Ожидаемые поступления по месяцам на 6 мес. «+ По договору из реестра» — график по старому договору на остаток.
- **`expectedPayments(ctx, from, to, opts)`** — экспорт модуля для прогноза денег (подключение — `CORE-REQUESTS.md`, п. 1).
- **Документы** (`crmdocs`, руководители и секретарь): шаблоны с полями `{{заказчик}}`, `{{сумма_прописью}}`, `{{график}}`… (список полей — в форме шаблона). Договор и ДС — HTML для печати/PDF; АВР и счёт — **данные для бухгалтера** по этапу оплаты + CSV (`;`, UTF-8 BOM) для 1С — официальные документы выписываются в 1С. Встроенные шаблоны можно менять и сбрасывать, можно добавлять свои. Значения экранируются.
- **Счётчики** (`ui.setBadge`): лиды с наступившим «следующим контактом» (или новые без контакта > 3 дней); платежи «пора выставлять акт» + просроченные (только руководителям).
- **Права на сервере**: руководители — всё; секретарь — лиды (чтение/запись, без удаления и подписания) и документы; ПМ — только чтение лидов, где он ответственный или ПМ/ГИП связанного проекта; бухгалтер, ГИП, руководитель раздела, сотрудник — 403. КП и договоры ядра отдаются только через `/api/crm/meta` (на сайте ERP `/api/proposals` — 404).

## Обращения (WhatsApp) — 13.10.2026

У бюро есть отдельный номер WhatsApp («архивариус»). Служба-мост (отдельный процесс координатора, не в этом репозитории) читает номер и шлёт **личные** сообщения в ERP; здесь — только сторона ERP (без npm-зависимостей и кода WhatsApp). Сообщения от людей, которых нет среди текущих сделок, становятся обращениями в «Коммерции».

Файлы: `inbox.js` (приём, диалоги, действия), `domain.js` (телефон `normPhone/phonesIn/fmtPhone`, ключевые слова `INBOX_WORDS/inboxScore/inboxMark`), `ui.js` (разделы `crminbox`, `crmdialog`, блок в карточке сделки), `tests/inbox_test.js`.

### Формат запроса приёма (для моста)

```
POST http://<сайт «Финансы»>/api/crm/inbox/ingest        (боевой: порт 3000; crm на сайте ERP нет — там 404)
Authorization: Bearer most_<64 hex>                       ключ ИИ владельца (Настройки → ключи ИИ); X-Requested-With с ключом не нужен
Content-Type: application/json; charset=utf-8

{
  "source": "whatsapp",                                   // только whatsapp (можно не указывать)
  "contact": {
    "extId": "77011234567@s.whatsapp.net",                // JID контакта, обязателен; «:12» (номер устройства) отбрасывается
    "phone": "+7 701 123-45-67",                          // необязателен: если пусто — берётся из JID …@s.whatsapp.net / …@c.us; у …@lid телефона нет
    "name": "Имя из WhatsApp"                             // необязательно
  },
  "messages": [                                           // 1…100 сообщений одного контакта
    {
      "extId": "3EB0C767D26A1B2C3D4E",                    // id сообщения WhatsApp, обязателен — по нему отсекаются дубли
      "ts": 1791800000,                                   // обязателен: Unix-секунды, миллисекунды или ISO-строка
      "fromMe": false,                                    // true — исходящее (ответ бюро)
      "text": "Здравствуйте, нужен проект…",              // до 8000 знаков; для вложения — подпись
      "kind": "text",                                     // text | image | doc | audio | video (иное → text, с файлами → doc)
      "files": [ { "name": "ТЗ.pdf", "type": "application/pdf", "data": "<base64>" } ]   // до 10 на сообщение
    }
  ]
}
```

Ответ `200`: `{ ok, inboxId, created, status: "new" | "lead" | "ignored", leadId, added, duplicates, files, rejectedFiles: [{ extId, name, reason }], score, words }`.

- **Повторная отправка** того же `messages[].extId` тому же контакту — не дубль: `added: 0, duplicates: N`. Пачку можно слать повторно целиком (после сбоя связи) и с перекрытием.
- **Группы**: `contact.extId`, оканчивающийся на `@g.us` (а также `@broadcast`, `@newsletter`), — `400` «Групповые чаты и рассылки сюда не принимаются… группы принимает модуль „Проекты“ (pm)». Мост должен слать группы в pm, сюда — только личные чаты.
- **Лимиты**: больше 100 сообщений — `413`; файлов в запросе больше 25 МБ — `413`; тело JSON целиком ядро ограничивает 32 МБ (≈ 24 МБ файлов в base64) — иначе `400 too large` от ядра, поэтому большие вложения лучше слать по одному сообщению на запрос. Нет `contact.extId` / `messages` / `extId` или `ts` сообщения, больше 10 файлов в сообщении — `400`; запрос с ошибкой не принимается и частично.
- **Файлы**: ≤ 20 МБ каждый; картинки (jpg, png, webp, gif), PDF, офисные (docx, xlsx, pptx, doc, xls, ppt), dwg, голосовые и видео (ogg/opus, mp3, m4a, mp4). Расширение — из имени, иначе из MIME (`type`); сигнатура содержимого сверяется с расширением. Файл, который не подошёл (тип, сигнатура, размер, пустой), **не срывает приём**: сообщение сохраняется, файл попадает в `rejectedFiles` с причиной и виден в ленте как «файл не принят». На диске: `DATA_DIR/crm-files/inbox/<id диалога>/<ключ>`, в базе — ключ, имя, размер, sha256.
- **Права**: приём — только `owner` / `partner` (вошедший паролем или по ключу ИИ; ключ действует от имени владельца). Остальным `403`, без входа `401`. Ключу ИИ ядро запрещает `DELETE` — приёму и разбору это не мешает.

### Что происходит с сообщениями

- Диалог ищется по `source + extId`, затем по нормализованному телефону (тот же человек с другим JID попадает в тот же диалог). Телефон: только цифры, `8XXXXXXXXXX` и `7XXXXXXXXX` (без кода страны) → `7XXXXXXXXXX`.
- `crmInbox`: `id, source, extId, phone, name, leadId ('' — пока не сделка), status: new | lead | ignored, firstAt, lastAt, count, unread, score, words, firstText, lastText, linkedBy ('auto' — по телефону)`. `crmInboxMessages`: `id, inboxId, extId, ts (ISO), fromMe, text, kind, files`.
- **Телефон есть в текущей сделке** (в полях лида «Телефон / почта» или «Контактное лицо»; сделка не в «Отказе» — сначала сделки в работе, затем с подписанным договором): диалог сразу `lead`, привязан к ней (`leadId`), в истории сделки — запись; новой сделки нет. Иначе — `new`, список «Обращения».
- **«Похоже на заказ»** — `score` = сколько разных групп ключевых слов встретилось во входящих сообщениях (проект/жоба, эскиз, рабочий проект, участок, га/сотки, м², коттедж, ЖК/тұрғын үй, гостиница, стоимость/баға, КП, договор/шарт, сроки/мерзім, архитектура, интерьер, строительство, заказ/тендер, экспертиза): 2+ — «похоже на заказ», 1 — «возможно, заказ». Только подсветка — ничего не отбрасывается автоматически.
- **«Не заказ»** (`ignored`): новые сообщения контакта сохраняются, но диалог не возвращается в новые и не привязывается к сделкам, пока метку не снимут вручную.

### Экран и API разбора

- Меню «Обращения» с бейджем (число новых), вкладка «Обращения» рядом с «Канбан / Таблица» и строка «новых обращений: N» в шапке воронки. Список: имя, телефон, первое сообщение, время, метка заказа и слова, статус, сделка. Карточка диалога (`#/crmdialog?id=`): лента сообщений с файлами (только чтение, ключевые слова подсвечены). В карточке сделки — блок «Переписка WhatsApp» (последние 5 сообщений, ссылка на диалог).
- `GET /api/crm/inbox[?status=new|lead|ignored]` → `{ items, counts, canEdit }`; `GET /api/crm/inbox/:id` → диалог + `messages` (последние 500); `GET /api/crm/inbox/:id/files/:key` — файл (картинки и PDF — inline, остальное — вложение).
- `POST /api/crm/inbox/:id/lead` `{ client?, contact?, object?, objectType?, track?, note? }` — **«Создать сделку»**: лид «Новый», заказчик = имя, телефон, источник `WhatsApp`, заметка = первые 5 входящих сообщений; диалог → `lead`. Повторно — `409`.
- `POST /api/crm/inbox/:id/link` `{ leadId }` — **«Привязать к сделке…»**; `{ leadId: "" }` — отвязать (диалог снова `new`).
- `POST /api/crm/inbox/:id/ignore` `{ ignored: true | false }` — **«Не заказ»** / вернуть в обращения; `POST …/read` — сбросить «непрочитанные».
- Счётчики: `GET /api/crm/badges` → `crminbox` (новых), `GET /api/crm/funnel` → `inbox: { new, lead, ignored }`, `GET /api/crm/leads/:id` → `whatsapp: [{ id, name, phoneText, count, lastAt, messages }]`. Источник `WhatsApp` добавлен в справочник источников лида — попадает в статистику источников маркетинга (`mkt.leadsBySource` читает `crmLeads.source` как есть) и в воронку/панель директора без правок у них.
- Права: читают и разбирают — руководители и секретарь (как лиды); ПМ видит только переписку своих сделок (чтение); бухгалтер, ГИП, руководитель раздела, сотрудник — `403`. Удаление сделки возвращает её переписку в «Новые».
