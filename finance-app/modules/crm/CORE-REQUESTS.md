# Запросы потока C (crm) к ядру

1. **Прогноз денег** (`lib/domain.js → cashForecast`, маршрут прогноза в `server.js`): добавить ожидаемые поступления по графикам платежей —
   `MODULE_BY_ID.crm && MODULE_BY_ID.crm.expectedPayments(ctx, from, to)` → `[{ date, planned, late, amount, withVat, status, invoiced, label, client, contractId, leadId, paymentId }]`.
   Чтобы не считать дважды: пропускать строки с `invoiced: true`, если по этому договору (`contractId`) акт уже есть в `db.docs`; и не брать `contracts.expectedDate/toPay` для договоров, у которых есть строки графика (`contractId`). Просроченные неоплаченные приходят с `late: true` и датой `from`.
   Функции нужен только `ctx.db`, `ctx.D`, `ctx.today` — можно передать облегчённый ctx.
2. **(по желанию) «Пора выставлять акт» → очередь бухгалтера**: сейчас бухгалтер получает данные из «Коммерция → Документы» (HTML + CSV для 1С). Если нужна строка в `db.docs` (очередь к бухгалтеру в «Финансах»), нужна функция ядра вида `ctx.core.requestDoc({ type: 'act', client, contractId, amount, note })` — модули в чужие коллекции не пишут.
3. Включить модуль `crm` в «Настройки → Модули» после приёмки.
4. **(предложение, ждёт согласования директора) Сервисный токен для автоматической публикации КП.** Генераторы КП директора (`Коммерческие\<проект>\_src\make_*.js`) после сборки PDF/DOCX сами вызывают `POST /api/crm/leads/:id/kp/external` — без ввода пароля. Сейчас ядро отвечает 401 до модуля (`if (!user)`), поэтому нужна маленькая правка ядра:
   - В `api()` перед `if (!user) return 401`: если cookie-пользователя нет, есть заголовок `Authorization: Bearer mostsvc_…`, сайт `fin` (офис; туннель всегда уходит в ERP) — спросить модули: `m.serviceAuth && m.serviceAuth({ db, store }, token, { method, parts, ip })` → псевдопользователь `{ id: 'svc-<id>', role: 'service', name: 'Сервис: <имя токена>', service: { tokenId, scopes } }` или `null` (тогда 401). Роли `service` нет в `D.ROLES` — `D.can` везде `false`, общие маршруты ядра ему закрыты; модуль пускает его только в свои разрешённые маршруты.
   - Модуль crm (сделаю после согласования): коллекция `crmTokens` `{ id, name, scopes: ['kp.publish'], hash: sha256(секрет), tail (последние 4 символа), createdAt, createdBy, lastUsedAt, lastIp, revokedAt }`. **Не в `settings`**: `GET /api/settings` на сайте ERP открыт всем пользователям — даже хэши туда класть не стоит. Секрет — 32 случайных байта, показывается один раз при выдаче. Выдаёт и отзывает руководитель (owner/partner) в «Коммерция → Публикация КП»; каждое использование — в журнал (`audit` от `svc-<id>`), видно «когда и откуда последний раз».
   - Права токена `kp.publish`: только `POST /api/crm/kp/publish` — найти лид по `leadId` / `kpNo` / точному «заказчик + объект» или создать новый (статус «Расчёт», ответственный — выдавший токен), затем внешняя редакция КП с файлами (та же логика и проверки, что у `…/kp/external`; повтор той же публикации редакцию не множит). Читать лиды, менять статусы, удалять, подписывать — нельзя.
   - На стороне скрипта: адрес `http://fin.most` (или `localhost:3000` на сервере), токен — из переменной окружения `MOST_KP_TOKEN` или файла `%USERPROFILE%\.most\kp-token`, не в папке `_src` и не в git. Заголовки `Authorization: Bearer …` и `X-Requested-With: fetch` (CSRF-проверка ядра остаётся; браузер Bearer сам не подставляет, так что CSRF через токен невозможен).
   - Правка ядра — ~10 строк в `server.js` (+ строка в `docs/ARCHITECTURE.md` про `serviceAuth`). Альтернатива без ядра — отдельный пользователь-«робот» с паролем в файле у скрипта — хуже: полный доступ секретаря к лидам и документам, пароль в открытом виде.
