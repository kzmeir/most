# Пульс-доска портфеля РП — набросок

Новый вид в модуле pm (`#/rp/pulse`, рядом со «Сводкой»/«Кварталом»), только руководители. Задача — чтобы ТИХИЕ ЗАСТРЯВШИЕ проекты были видны, а не «тихий заказчик = пауза = само рассосётся».

## Колонки (строка = проект)
| Колонка | Источник |
|---|---|
| Проект / заказчик | pm + единый справочник заказчиков |
| Реальный этап / % | сканер (артефакты на диске), сверено с ERP |
| **Дней без движения** | сканер: сегодня − дата последнего значимого файла/оплаты |
| **Чей ход** | сканер: наш / заказчик-госорган |
| Буфер (температура) | `PM.health` — зона (зелёная…чёрная), % съеденного буфера |
| Срок / прогноз | pm |
| Красные флаги | правило движения (ниже) |

Сортировка по умолчанию: сначала красные (застрявшие и просроченные), потом по «дней без движения» убыв.

## Красным (видно сразу)
- **≥90 % и стоит** (нет движения >30 дн) → авто-эскалация.
- **Пауза без даты возврата** → авто-красный (правило: пауза только с причиной И датой).
- **«Ждём заказчика» давно без даты** → это задача ГИПу додолбить заказчика с датой, а не пассивная пауза.
- **Расхождение ERP↔диск**: в ERP 0 %/ранний этап, а на диске поздние артефакты (или наоборот).
- Срок по договору прошёл.

## Правило движения (зашито в логику сканера/доски)
1. Молчание заказчика ≠ пауза. Это открытая задача ГИПу: «додолбить», с датой следующего контакта.
2. Пауза — только с явной причиной И датой возврата. Нет даты → авто-красный.
3. ≥90 % и встал → авто-эскалация руководителю.

## Данные и обновление
- Сканер (`status_scan.js`) гоняется по папкам `Z:` + данные ERP (оплаты/акты) → реальный этап, дни без движения, чей ход, аномалии.
- Доска читает результат сканера; запись статусов в pm (`PUT /pm/items` + журнал) — **отдельным действием и только по явному «да» директора** (в пилоте — превью, без записи).
- Привязка проект↔папка: завести поле `folder` в карточке pm (сейчас пустое) или матчить по номеру/имени.

## Статус (пилот)
MVP сканера + карта этап→артефакт готовы, пилот по 6 прогнан в превью (см. отчёт). Сам вид доски в UI — следующий шаг после приёмки логики; здесь — набросок и визуальный макет для директора.
