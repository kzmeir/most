# Инструкция сисадмину — постоянный сервер MOST Финансы

Для пользователей — `README.md`. Здесь — как поднять сервер так, чтобы он работал круглосуточно, сам
перезапускался после сбоя или перезагрузки, и как проверить, что бэкапы и уведомления действительно работают.
Приложение — один процесс Node.js без npm-зависимостей и без внешней базы данных: вся база — один файл
`data/db.json`.

Два варианта. Docker на Synology (MostServer) — предпочтительный: NAS работает круглосуточно, Container
Manager сам поднимает контейнер после перезагрузки. Облачный VPS — если понадобится доступ не из офисной сети
без Cloudflare Tunnel, или Synology недоступен.

## Вариант 1. Docker на Synology (MostServer)

1. **Container Manager** (бывший Docker) — установите из Центра пакетов DSM, если ещё не установлен.
2. Скопируйте папку `MOST-Финансы` (эту, `finance-app`) на NAS, например в `/docker/most-finance`
   (через File Station или `\\MostServer\docker\most-finance` по сети).
3. Порты DSM **5000/5001 заняты** — не переопределяйте `PORT` на них. По умолчанию приложение слушает 3000
   внутри контейнера, наружу на NAS — тоже 3000 (`docker-compose.yml`, переменная `PORT` меняет только внешний порт).
4. Запуск:
   - Через интерфейс: Container Manager → **Проект** → **Создать** → путь к папке с `docker-compose.yml` → «Собрать».
   - Или по SSH на NAS: `cd /volume1/docker/most-finance && docker compose up -d`.
5. Первый запуск: откройте `http://MostServer:3000` (или IP NAS), создайте аккаунт владельца.
6. Автозапуск после перезагрузки NAS: Container Manager → проект `most-finance` → включите
   «Запускать контейнер автоматически» (включено по умолчанию политикой `restart: unless-stopped` в compose-файле;
   после первого ручного `docker compose up -d` Docker перезапускает его сам, включая после ребута NAS,
   пока запущена служба Docker — она стартует с NAS автоматически).
7. **Проверка живости**: `docker compose ps` — контейнер должен быть `healthy` (healthcheck дергает `/api/status`
   каждые 30 сек). Логи: `docker compose logs -f most-finance`.
8. Обновление кода: скопируйте новую версию файлов поверх старых (данные лежат в `data/` внутри той же папки —
   их менять не нужно), `docker compose restart most-finance`.

**Не задавайте `DEV_USER`** ни в `docker-compose.yml`, ни в окружении контейнера — это отключает пароли
(режим только для разработки на своём компьютере, см. `docs/ARCHITECTURE.md`). Файл `docker-compose.yml` в
репозитории его не задаёт — так и должно оставаться.

### Постоянный туннель Cloudflare в Docker (вариант вместо `start-internet.bat`)

Блок `cloudflared` в `docker-compose.yml` закомментирован — включите, если нужен доступ из интернета без VPN:

1. В [Cloudflare Zero Trust](https://one.dash.cloudflare.com/) → Networks → Tunnels → **Create a tunnel**,
   скопируйте токен.
2. Publiс Hostname туннеля → сервис `http://most-finance:3000` (имя контейнера в той же docker-сети, порт — внутренний).
3. Создайте файл `.env` рядом с `docker-compose.yml`: `CLOUDFLARE_TUNNEL_TOKEN=<токен>` (не коммитить, он уже в `.gitignore` как часть `data/`? — проверьте: если нет, добавьте `.env` в `.gitignore` отдельно, это секрет).
4. Раскомментируйте блок `cloudflared` в `docker-compose.yml`, `docker compose up -d`.

С именованным туннелем сервер сам ставит `TRUST_PROXY` не нужен переменной — в Docker-варианте это не проверяется
автоматически, как в `serve-internet.js`; убедитесь, что если туннель включён, реальный IP приходит в заголовке
`CF-Connecting-IP` (Cloudflare добавляет его сам) — сервер уже учитывает его при `TRUST_PROXY=1`. Добавьте
`TRUST_PROXY=1` в `environment:` контейнера `most-finance`, если используете туннель в Docker-варианте.

## Вариант 2. Облачный VPS (без Docker)

Для команды, у которой нет Synology/Windows-сервера, подойдёт недорогой VPS (Ubuntu 22.04+).

1. Установите Node.js 22 LTS: `curl -fsSL https://deb.nodesource.com/setup_22.x | sudo bash -` затем `apt install nodejs`.
2. Скопируйте папку `finance-app` на сервер (`scp -r` или `git clone` приватного репозитория).
3. Автозапуск и перезапуск при падении — systemd-юнит `/etc/systemd/system/most-finance.service`:
   ```ini
   [Unit]
   Description=MOST Финансы
   After=network.target

   [Service]
   WorkingDirectory=/opt/most-finance
   ExecStart=/usr/bin/node server.js
   Environment=PORT=3000
   Restart=always
   RestartSec=5

   [Install]
   WantedBy=multi-user.target
   ```
   `systemctl daemon-reload && systemctl enable --now most-finance`.
4. **Не открывайте порт 3000 в интернет напрямую** — только через Cloudflare Tunnel (`cloudflared` как systemd-сервис
   или Docker, см. вариант 1) или VPN. Файрвол (`ufw`) пропускает только SSH и, при необходимости, 443 для туннеля.
5. Бэкапы — см. ниже; путь к Google Drive для компьютера недоступен на Linux-VPS без десктопного клиента, поэтому
   на VPS используйте вместо `backup-gdrive.ps1` любой облачный синк каталога `data/backups/` (rclone, Dropbox CLI
   и т.п.) — настраивается отдельно, не входит в эту поставку.

## Доступ из интернета — если не через Docker/VPS, а с Windows-сервера

Подробности и постоянный адрес (именованный туннель) — в `README.md`, раздел «Доступ из интернета». Коротко:
`start-internet.bat` поднимает `node tools/serve-internet.js`, который держит и сервер, и `cloudflared`, сам
перезапускает оба при сбое, и переживает запуск не из своей папки (`pushd` в `.bat` и абсолютные пути в
`serve-internet.js` от `__dirname` — проверено, путь к серверу и к `tunnel.txt` не зависит от текущей директории).
Автозапуск при включении MostServer — `install-autostart.bat` (задача Планировщика Windows, `ONLOGON`).

**Проверка (важно для безопасности):** режим `DEV_USER` (вход без пароля) должен быть недоступен, если сервер
поднят за туннелем — ядро уже это проверяет (`server.js`, функция `devUser`: отказ при `TRUST_PROXY`,
`CF-Connecting-IP` или `X-Forwarded-For`, и только с адреса `127.0.0.1`). Тест на это — в `tests/api_test.sh`,
раздел «DEV_USER и туннель»; прогоняйте после любых изменений в `server.js`.

## Бэкапы

- **Локально, автоматически** — уже работает: первая запись каждого дня копирует `data/db.json` в
  `data/backups/`, хранится 60 копий (`lib/store.js`). В Docker-варианте это внутри того же смонтированного тома —
  бэкапы переживают перезапуск контейнера.
- **В Google Drive, ежедневно** (для Windows-сервера с установленным Google Drive для компьютера, папка
  `G:\Мой диск\...`): скрипт `tools/backup-gdrive.ps1` уже есть, запускается вручную через `backup-gdrive.bat`.
  Чтобы он выполнялся сам каждый день — запустите `install-backup-task.bat` **от имени администратора** один раз:
  он регистрирует задачу Планировщика Windows (`schtasks`) на ежедневный запуск в 03:00. Проверить: Планировщик
  заданий → «MOST Финансы — бэкап»; запустить сейчас — `schtasks /Run /TN "MOST Финансы - бэкап"`; удалить —
  `schtasks /Delete /TN "MOST Финансы - бэкап" /F`.
- **На Synology** — если сервер в Docker на NAS, проще завести собственную задачу NAS: Панель управления →
  Backup → Hyper Backup на папку с `data/` (или Task Scheduler DSM с `tar`/`rsync` в расписании) — надёжнее, чем
  тянуть Google Drive для компьютера на NAS.
- **Проверка восстановления** (сделайте один раз после разворачивания и держите в памяти процедуру):
  1. Остановите сервер (`docker compose stop most-finance` или закройте окно `start.bat`).
  2. Скопируйте нужный файл из `data/backups/db-*.json` поверх `data/db.json`.
  3. Запустите сервер снова, войдите — данные должны быть на момент копии.
  Через интерфейс восстановление проще: Настройки → Резервные копии → «Восстановить из файла» (владелец) — сама
  делает копию `before-restore` перед заменой, ничего вручную останавливать не нужно. Тест на этот путь целиком
  (бэкап → порча данных → восстановление → проверка) уже в `tests/api_test.sh`, раздел «backup/restore».
  Тест логики самого `backup-gdrive.ps1` (сборка zip, `db.json` без сессий) — `tests/backup_gdrive_test.sh`,
  прогоняет скрипт на тестовых путях, ничего не трогая на реальном MostServer/Google Drive.

## Уведомления в Telegram

Модуль «Сервис» (`modules/sys`) отправляет уведомления через Telegram-бота. Настройка — экран
**«Состояние системы»** в интерфейсе (виден только владельцу):

1. Создайте бота: в Telegram напишите **@BotFather** → `/newbot` → следуйте подсказкам → скопируйте токен вида
   `123456:ABC-...`.
2. Вставьте токен на экране «Состояние системы» → «Бот Telegram» → «Сохранить токен». Токен хранится в
   `data/db.json` (не в git — см. `.gitignore`), в ответах API отдаётся только последними 4 символами.
3. У каждого сотрудника, которому нужны уведомления: попросите написать боту `/start` (иначе бот не может писать
   первым), узнать свой chat_id через **@userinfobot** (или из ответа `getUpdates` у своего бота), и внести пару
   `id_пользователя chat_id` на том же экране.
4. Кнопка «Тест уведомления себе» шлёт тестовое сообщение владельцу — проверить, что токен и chat_id верны.
5. Очередь (`sysOutbox`): каждое уведомление — «ожидает» → «отправлено» / «ошибка» (после 5 неудачных попыток)
   / «пропущено» (нет токена или chat_id). Неудачные повторяются автоматически раз в 5 минут, пока не наберётся
   5 попыток; кнопка «Повторить» — вручную сразу.

Другие модули вызывают уведомления так: `ctx.modules.sys.notify(ctx, { userIds: [...], text: '...', link: '...' })`
(см. `docs/ARCHITECTURE.md`, таблица событий).

## Экран «Состояние системы»

Владельцу: версия приложения, путь и размер `data/db.json`, число и время последнего локального бэкапа, текущий
адрес туннеля (если запущен), явное предупреждение, если `DEV_USER` почему-то включён на этом сервере, и очередь
уведомлений с возможностью повторить отправку. `GET /api/sys/status` — только владелец.

## Чек-лист перед сдачей в работу

- [ ] `DEV_USER` нигде не задан в проде (ни в `docker-compose.yml`, ни в `.bat`/systemd для боевого сервера).
- [ ] Порт 3000 (или выбранный) не проброшен в интернет напрямую — доступ только через Cloudflare Tunnel или VPN.
- [ ] `docker compose ps` показывает `healthy`, либо (без Docker) окно `start.bat`/`start-internet.bat` не закрыто,
      либо systemd-юнит `active (running)`.
- [ ] Автозапуск после перезагрузки проверен (перезагрузили сервер/NAS — приложение поднялось само).
- [ ] Ежедневный бэкап в Google Drive (или Hyper Backup на Synology) настроен и один раз проверен вручную.
- [ ] Восстановление из копии один раз проверено на тестовой базе (не на боевой!).
- [ ] Токен Telegram-бота и хотя бы один chat_id внесены, тестовое уведомление дошло.
- [ ] `bash tests/api_test.sh` — все проверки зелёные (запускать на тестовой базе, не на боевой).
